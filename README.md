# @syldel/trading-shared-types

Shared TypeScript types between the NestJS trading API and the Ionic/Capacitor/Angular
mobile app. Zero runtime dependencies, zero framework decorators — only `type` / `interface`
(plus a couple of `const` lookup maps for chart intervals).

## Contents

- `strategy-engine.type.ts` — strategy rule AST (`RuleNode`, `Operand`, `IndicatorOperand`, `ComparisonCondition`, `TrendCondition`, `LogicalGroup`...)
- `exchange-config.interface.ts` — exchange/pair/strategy config (`IExchange`, `IExchangeStrategy`, `LatentOrderStrategy`, `ProtectiveOrderStrategy`...)
- `exchange-meta.type.ts` — contract for `GET /exchanges/meta` (`ExchangesMetaResponse`, `IndicatorMetadata`, `StrategyMeta`...)
- `chart.type.ts` — `ChartInterval`, `ReadableChartInterval`, `chartIntervalMap`, `chartIntervalToMinutes`
- `analysis-candle.type.ts` — `AnalysisCandle`
- `analysis.type.ts` — contract for `POST /analysis` (`AnalysisRequest`, `AnalysisResponse`, `IndicatorRequest`...)

## Installing this package

### From Git (recommended, pinned to a tag)

```bash
npm install "git+ssh://git@github.com/Syldel/trading-shared-types.git#v0.2.1"
# or over HTTPS:
npm install "git+https://github.com/Syldel/trading-shared-types.git#v0.2.1"
```

npm automatically runs the `prepare` script (= `npm run build`) right after cloning,
so `dist/` gets generated even though it's not committed (see `.gitignore`).

⚠️ Always pin to a tag (`#v0.1.0`), never a branch (`#main`): otherwise `npm install`
can resolve a different commit at different times in Nest vs. Ionic — exactly the
drift this package exists to prevent.

### Locally, during dev (both repos on your machine)

```bash
npm install file:../trading-shared-types
```

Handy to iterate fast, but **never commit** a `package.json` pointing to a local
`file:` path — it breaks the install for anyone without that exact folder layout.
Keep `file:` for your own machine; use a Git tag everywhere else (CI, other machines).

## Usage in Nest

```ts
import { RuleNode, IExchangeStrategy } from '@syldel/trading-shared-types';
```

## Usage in Angular / Ionic

```ts
import { RuleNode, Operand, ChartInterval } from '@syldel/trading-shared-types';
```

Angular (esbuild) and Nest (ts-node / webpack) both consume the same `dist/` build
(ESM + CJS + `.d.ts`) generated by `tsup` — no extra bundler config needed on the
consumer side.

## Development setup

```bash
git clone git@github.com:Syldel/trading-shared-types.git
cd trading-shared-types
npm install          # installs deps + devDeps, triggers "prepare" (= build only)
npm run husky:init   # activates the pre-commit hook — see "Git hooks" below
```

`npm install` alone is **not** enough to get the pre-commit check working — see why below.

```bash

```

## Git hooks (Husky)

### What `npm run verify` does

```bash
npm run verify   # = npm run typecheck && npm run lint && npm run build
```

One command, three gates: type errors, lint errors, and a broken build all block on this.
This is the command wired into the `pre-commit` hook (see below), and also what
`prepublishOnly` runs before any future `npm publish`.

### Content of `.husky/pre-commit`

```sh
#!/usr/bin/env sh
npm run verify
```

That's the entire hook. If `verify` exits non-zero (type error, lint error, or build
failure), Git blocks the commit.

### Why activation is manual, and what happens on a fresh clone

On a **new machine**, cloning the repo does **not** automatically enable the hook:

```bash
git clone git@github.com:Syldel/trading-shared-types.git
cd trading-shared-types
npm install
```

At this point:
- `npm install` installs all dependencies **and** devDependencies (this is your own repo,
  not a consumer installing it as a dependency) — so `husky` is present in `node_modules`.
- The `prepare` script runs automatically and does `npm run build` — it does **not**
  touch Git hook configuration.
- `git config core.hooksPath` is still unset. The hook is **not active yet.**

You must run one more command, once per machine/clone:

```bash
npm run husky:init
```

This runs the `husky` CLI, which sets:

```bash
git config core.hooksPath .husky
```

Verify it worked:

```bash
git config core.hooksPath
# should print: .husky
```

### Why `husky:init` isn't wired into `prepare` or `postinstall`

It would be simpler to auto-run on every `npm install` — but `prepare` (and `postinstall`)
also fire when this package is installed **as a dependency** by Nest or Ionic (via
`git+ssh` or `file:`). Those consumers don't have `husky` in their own `node_modules`
(it's only a devDependency of *this* repo), so an automatic `husky` call there would
fail and break their install entirely.

So the split is intentional:
- `prepare` → `npm run build` only (needed by consumers, harmless for them).
- `husky:init` → manual, one-time, per clone, only relevant to people developing
  *this* repo, never triggered by a consumer's install.

The trade-off: you have to remember to run `npm run husky:init` after every fresh
clone. Forgetting it doesn't break anything immediately — it just means commits on
that machine won't be gated by `verify` until you run it.

### About `.husky/_`

After running `husky:init`, Git points `core.hooksPath` at `.husky`, and Husky
generates an internal wrapper directory `.husky/_` (implementation detail, regenerated
automatically — this is why it's excluded in `.gitignore`). The file you actually
edit and that matters is `.husky/pre-commit` itself, which **is** committed.

## Initializing the repo (first time only)

```bash
git init -b main
npm install                     # generates package-lock.json (needed by `npm ci` in CI)
npm run husky:init              # activates the pre-commit hook (needs .git to already exist)
git add -A
git commit -m "chore: initial scaffold for shared trading types package"
git tag -a v0.1.0 -m "v0.1.0 — initial strategy/exchange/chart types"
git remote add origin git@github.com:Syldel/trading-shared-types.git
git push -u origin main --follow-tags
```

What's different from a plain `git init && git add -A && git commit -m "init"`:
- **`-b main`**: doesn't depend on your global Git config's default branch name (`master` vs `main`).
- **`npm install` before the commit**: generates `package-lock.json`, which must be committed —
  CI's `npm ci` needs it, otherwise the first run fails.
- **Conventional commit message** (`chore: ...`): useful now if you ever automate the
  changelog later (e.g. with `changesets` or `semantic-release`).
- **Annotated tag** (`-a` + `-m`) rather than a lightweight one: carries a message and
  author, useful in `git log --decorate` / `git show v0.1.0`.
- **`--follow-tags`**: pushes the tag together with the commit, in one push.

## Versioning a change

1. Edit the types in `src/`.
2. Commit your changes — `npm version` refuses to run on a dirty working directory:

```bash
   git add -A
   git commit -m "feat: describe what changed in the types"
```

3. Run the full check before touching the version number:

```bash
   npm run verify   # typecheck && lint && build
```

4. Bump the version, commit the bump, and tag it — all in one command
   (pick `patch` / `minor` / `major` per the semver rule below):

```bash
   npm version minor -m "chore(release): %s"
```

   `npm version` updates `package.json`/`package-lock.json`, creates a commit
   with that message (`%s` is replaced by the new version number), and creates
   a matching annotated tag (e.g. `v0.2.0`) — no need to run `git tag` separately.

5. Push the commit and the tag together:

```bash
   git push --follow-tags
```

6. In Nest and Ionic, bump explicitly on both sides:

```bash
   npm install "git+ssh://git@github.com/Syldel/trading-shared-types.git#v0.x.y"
```

### Semver rule to follow here

- **PATCH** (`0.1.0` → `0.1.1`): optional field addition, JSDoc, additive type that breaks nothing.
- **MINOR** (`0.1.x` → `0.2.0`): new exported type/interface, new optional field on an existing interface.
- **MAJOR** (`0.x.y` → `1.0.0`): renaming or removing a field, changing the shape of an existing type
  (e.g. the possible future move from `{ type: 'indicator'; name; period }` to
  `{ type: 'indicator'; indicator: { name; parameters } }` discussed earlier — **that's a
  breaking change**, so a major bump, and both apps must migrate in the same window so a
  strategy serialized by one version stays readable by the other).

## Future migration to a private npm registry

When it's worth it (a 3rd consumer, a growing team, or you no longer want installs to
depend on Git access to this repo):

1. Set up a private registry (GitHub Packages, private npm, or self-hosted Verdaccio).
2. Add to `package.json`: `"publishConfig": { "registry": "https://npm.pkg.github.com" }`
   (and flip `"private": true` back to `false`).
3. `npm publish` (the `prepublishOnly` script already runs `verify` beforehand).
4. Replace the `git+ssh://...` dependencies with a regular
   `"@syldel/trading-shared-types": "^0.2.0"` in both consumers.

No code change is needed in `src/` for this migration — only the distribution method changes.
